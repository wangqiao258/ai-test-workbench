# 执行任务：管理与观测的边界分析

> 2026-10-23 15:40。问题："工作台有没有必要做自动化测试任务的管理和观测？"
> 本文先回到已定角色与决策，再用线上真实数据回答，最后给边界与最小闭环。
> 结论一句话：**"管理"不做（与决策 #6 冲突、无消费者）；"观测"必须做，且它是 P1 的欠账，不是 P2 的新功能。**

---

## 1. 定位回顾：谁做决策，谁记账

`docs/部署与执行引擎设计.md` §2 的角色表（2026-10-23 与用户定案）：

| 角色 | 职责 | 明确不做 |
|---|---|---|
| AI | 分析师：出用例/断言/掩码（全是数据）、发起 run、读结果下结论、提 Bug | 不亲手执行、不写执行代码 |
| 平台 | 账本（契约/用例/结果/Bug/证据）+ 手脚（runner 执行/采集/回填） | **不做测试决策** |
| 用户 | 唯一质量门：审 Bug、拍板方向、给凭据 | 不做执行、不逐条审用例 |

两条直接相关的决策：

- **#6 触发方式：AI 随时发起（`POST /api/runs`），不要调度器。**
- **#7 修复验证 = 复跑产生新 execution，Bug 保持单轴不加状态。**

把两件事对齐后，"管理"这个词在定位里没有落点：

- 调度器、优先级、重试策略、定时回归 —— 本质是"决定跑什么、何时跑、失败要不要再跑"，**属于测试决策**，按 §2 归 AI，且 #6 已经明确否掉。
- 平台能做的是"记住这轮跑了什么、有没有跑完、为什么没跑完、把结果摆出来"——**那是观测**。

一句话划界：**平台负责"跑完了没有、卡在哪、为什么卡"；AI 负责"跑什么、要不要重跑"；用户只看"红了没有"。**

---

## 2. 证据一：当前的量级不需要"管理"

线上库（`GET /api/runs?project_id=1`，2026-10-23 15:36 取数）：

| 维度 | 实测 | 含义 |
|---|---|---|
| run 总数 | 12 个（14:04–15:36，92 分钟内） | 全是边做边发，不是批量排产 |
| `trigger` | **ai 12 / manual 0** | 没有人在"管理任务" |
| `created_by` | ai:workbuddy 12 | 单一发起方 |
| `scope` 键 | **case_ids 12 / batch 0 / module 0 / group 0** | 批次、模块、分组三种批量发起**一次没用过** |
| 单 run 规模 | 1–21 条（多数 1–9 条） | 没有队列压力 |
| 单轮耗时 | 1–23 秒（run 8：9 条 9 秒；run 7：21 条 23 秒） | 不存在"排队等执行" |
| 项目数 | 1 个 | 单项目、单 runner、SQLite 单写者 |

**推论**：排队、优先级、并发编排、重试策略、定时调度——这五项能力今天找不到任何一个使用者。做出来就是给一个人用的 Jenkins，维护成本却由平台长期承担。

## 3. 证据二：观测已经欠账，今天就有两个僵尸 run

### 3.1 现象

| run | 名称 | 开始 | 已完成 execution | 最后一条 | 15:37:59 状态 |
|---|---|---|---|---|---|
| 11 | 全量基线（21 条） | 15:00:02 | 8 / 21 | 15:00:10 | **running（37 分 49 秒无进展）** |
| 12 | 服务器执行-21条（内网直连） | 15:35:59 | 1 / 21（blocked） | 15:36:30 | running |

run 11 的 8 条里其实是 **2 pass（29、31）、6 fail（30、32–36）**，但 `summary` 至今是
`{total:21, pass:0, fail:0, blocked:0, skipped:0}` —— 因为 **summary 只在 `finish` 时写**（`api/runs.py` 的 finish 端点），
中途死的这一轮在列表里长得像"刚创建、还没开始"。

### 3.2 四个今天答不出来的问题

| 问题 | 今天为什么答不了 | 证据（代码/数据） |
|---|---|---|
| 这一轮跑完了吗？ | 只有 `status`，没有进度；`running` 无法区分"在跑"和"死了" | run 11 停在 8/21 已 37 分钟 |
| 跑到第几条了？ | summary 只在 finish 写，中途恒为 0；要自己数 executions | run 11 summary 全 0，实测 8 条 |
| 谁在跑、跑在哪台机器、还活着吗？ | `runs` 表没有 `runner_id` / 心跳列 | `db.py:176-190`（14 个列，无 runner 身份） |
| 卡住了怎么办？ | 状态机不允许 running → 取消，只能改库 | `core/runs.py:94-101` 只有 4 条合法流转 |

配套的两个事实：

- **runner 进程死掉不会留痕**：`runner/__main__.py` 主循环只在正常走完时 `finish`；Ctrl+C / 关窗口 / 会话回收都没有 `finally` 兜底，run 就永久 `running`。
- **失败原因是自由文本**：run 6（2 blocked / 19 skipped / failed）能看懂"服务器容器连不上 443"，靠的是 runner 手写进 `summary.note` 的一句话，不是可聚合的字段。同样的现象换成 run 12 就只剩一条 `SSLMiddleware` 异常串。

### 3.3 网页端：逐条的账有，整轮的账没有

- `app.py` 路由表里**没有 `/runs`**，`templates/` 里也没有运行页；P2 计划里的"运行页签"尚未存在。
- 但 `/cases/<id>` 是有的：执行历史、分步结果、关联 packets 都能看（`templates/case_detail.html:60-76`）。

所以现状是：**用户想知道"某条用例跑过几次、结果如何"，能查；想知道"这一轮跑完了吗、红了哪几条"，只能问 AI，AI 再查一次 API。**
对"质量门"这个角色来说，门前的执行状态是空的。

## 4. 为什么这不是体验问题，而是 P2 的地基问题

1. **P2 的对比基准依赖 run 正常收尾**。设计 §7.1 的基准是"同 scope 上一次 `done` 的 run"。僵尸 run 永远不 `done`，基准会**静默退化**到更早的一轮，diff 出来的"新增失败/已修复"就是错的——而且错得看不出来。今天 `baseline_run_id` 12/12 为 null，说明这条链路还完全没被验证过。
2. **执行已经外包出去了，"跑完了没"必须由平台自证**。P1 之前 AI 亲手跑，进度在自己手里；P1 之后 AI 只剩 API 一个窗口。窗口缺进度和心跳，等于把"每步都要人盯"换成了"每一步都看不见"。
3. **僵尸不是边缘情况，今天占 2/12**。按当前实现，任何一次关窗口都会留一个。这不是"以后量大了再说"的问题。

## 5. 边界：什么进平台，什么留给 AI，什么不做

| 归属 | 内容 | 依据 |
|---|---|---|
| **平台做（记录/展示/兜底）** | run 列表与详情、进度、runner 身份与心跳、僵死标记、取消、失败原因分类、跨 run 对比（P2） | 全是"如实记录 + 摆出来"，不含测试判断 |
| **AI 做（决策）** | 跑哪些用例、跑几轮、失败是否重跑、什么时候发起回归 | §2 角色表 + 决策 #6 |
| **不做** | 调度器/定时任务、优先级队列、并发编排、自动重试策略、告警通道、metrics 与日志聚合 | #6 已否；单用户单 runner 无消费者；告警没有接收方（企业微信 connector 关） |

一个容易混的点：**"取消"不是管理，是兜底**。它不决定测什么，只是把占着 `running` 的僵尸收掉、把资源状态改回真实。所以归平台，且只允许 `running → failed`，理由必填。

## 6. 若要做：最小闭环（文件级清单）

只做"能回答 §3.2 四个问题"的量，不做管理中心。

| 动作 | 文件 | 内容 |
|---|---|---|
| 改 | `db.py` | `runs` 增 3 列（只增不删）：`runner_id TEXT`、`last_heartbeat_at TEXT`、`cancel_note TEXT` |
| 改 | `api/runs.py` | ①`claim` 收 `runner_id` 落库；②**回填 execution 带 `run_id` 时顺带刷新 `last_heartbeat_at`**（零新增端点）；③列表/详情返回派生 `progress{total,done}` 与 `stalled`；④新增 `POST /api/runs/<id>/cancel`（running→failed，note 必填） |
| 改 | `core/runs.py` | `is_stalled(row, now, threshold=90)` 纯函数 + `progress_of(total, done)`；状态机**不动**（cancel 复用已有 `running→failed`） |
| 改 | `runner/__main__.py` | 认领时上报 `runner_id = hostname:pid`；`try/finally` + SIGINT 兜底 `finish(failed, "runner 中断")` |
| 新增 | `templates/runs.html`、`app.py` 路由、项目页 tab | 只读列表（50/页、URL 即筛选）+ 详情（进度、失败分类、跳 execution）；**不放调度按钮** |
| 改 | `tests/verify_runs.py` | +约 20 项：僵尸判定、心跳刷新、取消后不可回填、进度派生、并发 claim 仍 409 |

顺序建议：先 1–4（数据与接口层，AI 立刻受益，不碰 UI），稳定几天再补 5。
