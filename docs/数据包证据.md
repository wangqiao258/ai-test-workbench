# 数据包证据：核实与改造（2026-10-22）

## 一、起因

用户反馈：平台上要求留的证据"感觉不全，不是一个完整的请求和响应"。

页面确实写着 `templates/interface.html:58` 的小标题 —— **验证证据（真实数据包）**。

## 二、核实结果：证据链三条

### 1. 页面承诺"真实数据包"，实际内容是状态码

接口 11 / 14 / 16 的 evidence 全文：

```
GET -> 200
```

10 个字符。没有路径、没有参数、没有响应体。

### 2. 全库量化：78% 无法复核

| 表 | 条数 | 中位长度 | 最短 | 含「请求行+状态码+响应体」 |
|---|---|---|---|---|
| interfaces | 161 | 398 字符 | 10 字符 | 35 条（22%） |
| bugs | 56 | 758 字符 | 197 字符 | 13 条（23%） |
| executions | 157 | 875 字符 | 77 字符 | 92 条（59%） |

按长度看 interfaces：<50 字符 17 条（11%）、<100 字符 25 条（15%）、<300 字符 56 条（35%）。
而这 161 条**全部**是 `verify_status=verified`。

### 3. 响应体在写进来之前就被截断了

`executions` id=117（用例 106「字典简表返回全量字典项且字段结构完整」）：

- 证据长度**正好 20000 字符**
- 开头：`REQ GET /admin-api/system/dict-data/simple-list ... (114471字符)`
- 结尾：`... 'label': '吨', ...}, {'dictTy` —— 停在半个 JSON 中间

114471 字符的响应，落库 20000。全项目搜 `20000` / `[:n]` / `truncate` / `截断`，
**平台代码里一处都没有**。结论：不是平台截的，是写入侧脚本自己 `[:20000]`。

同类症状（括号不平衡 = 半个 JSON）：接口 16 条（id 22/30/42/57/59/63/82/91/92/93/94/122/131/148/149/159）、
执行 37 条、Bug 5 条。

## 三、根因三层

### 第一层：判定把"有证据"等同于"字符串非空"

`api/interfaces.py` 原实现：

```python
has_evidence = bool((data.get("evidence") or "").strip())
...
"verified" if has_evidence else "unverified"
```

`GET -> 200` 通过判定，拿到 verified 身份，随后被当作"生成用例的可信信源"。

### 第二层：schema 里没有放数据包的字段

`interfaces` 表有 `req_headers / req_params / resp_example`，但那是**契约示例**
（应该长什么样），不是**某一次实测的报文**（当时到底发了什么、回了什么）。
后者只能硬塞进 `evidence` 一个 TEXT 槽。

### 第三层：展示层只露 220px

`static/style.css` 里 `pre.evidence { max-height: 220px; overflow: auto }`。
Bug 详情页用 `max-height:none` 全展开，接口页没有。

## 四、改造方案（用户选择：结构化数据包 + 存量不动）

### 表结构

新增 `packets` 表，请求与响应**逐字段分开存**：

```
req_method / req_url / req_query / req_headers / req_body
resp_status / resp_headers / resp_body / resp_body_file
resp_chars / resp_bytes / sha256 / duration_ms
completeness（full/partial，服务端算）/ missing / linked_type / linked_id
```

一个对象可以挂多条包（正常路径、401 对照、越权尝试……），`linked_type` 支持
interface / bug / execution。

### 完整度判定（`core/packets.py`）

| 级别 | 条件 |
|---|---|
| `full` | 请求方法 + 请求地址 + 响应状态码 + 响应体，四样齐 |
| `partial` | 缺任一项，`missing` 说明缺什么 |

例外：`204 / 304 / HEAD` 无响应体不算缺。缺请求头/响应头**不降级**（只记提示），
因为没头的包依然能复核返回内容。

### 永不截断

响应体超过 `INLINE_CHARS = 8192` 就落盘到 `data/uploads/packets/`，
DB 只存 `resp_body_file` + `resp_chars` + `resp_bytes` + `sha256`。
文件名由 `sha[:16]-字符数.txt` 拼成（内容寻址，重复提交不产生冗余），
不含任何用户输入，天然无路径穿越。

页面渲染时超过 `VIEW_CHARS = 20000` 只渲染前段，但**必须显式写明**
"预览只显示前 N 字符，本条共 M 字符"并给下载入口，同时注明"存储未截断"。
显示层截断与存储截断必须能被区分开——这是本次事故的教训。

### verify_status 的新判定

| 操作 | 结果 |
|---|---|
| 提交 full 包（挂 interface） | verified，刷新 verified_at |
| 提交 partial 包 | 状态不变，返回接口**真实当前状态** + hint |
| 只改 evidence 文本 | 状态不变（不升不降） |
| 改契约字段 | changed |
| 显式传 verify_status | 以调用方为准（仅用于导入历史） |

返回 `verify_status` 一律**回读库里的真实值**，不按本次包推断。曾写成"按本次包推断"，
导致给已验证接口补残缺包时返回 unverified，被测试抓到并修正。

### 存量策略

161 条一条不动（用户决定）。代价是那段不可复核的历史会留在库里，
所以详情页加了一条明确提示：

> 这条标着『已验证』，但库里没有原始报文。它是在引入数据包之前录的，
> evidence 只有一句话，**无法复核**。

让"看不见的债"变成"看得见的债"，比批量降级更符合当前阶段——用户还需要这些接口
作为生成用例的信源，一次性标红会让 78% 的接口失去可用性。

## 五、克制的地方

- 没有引入执行引擎。平台仍然只记录"我做了什么"，不负责"能不能跑"。
- 没有给 packets 加版本/差异对比。sha256 留着，将来要判断"两次实测是否同一个包"再往上做。
- 没有动 Bug 的审核流、分栏、批量。只是在 `has_evidence` 的口径里补了 packets
  （`core/lists.py` 的 `_BUG_EVI_SQL`）。

## 六、验证

`tests/test_packets.py` 90 项：core 校验/归一/完整度/落盘判定、API 写入与读取分档、
大响应逐字符比对、页面渲染、存量保护（161 条状态与 verified_at 全等）、删包清文件。

全套 9 个测试脚本 379 项全绿。

其中两处既有失败经核实**与本次改造无关**：用改动前的代码跑同一份库，`verify_split`
的"第 2 页条数"与 `verify_bug_views` 的"两页合计"同样失败，数字一致（9 条 / 40 条）。
原因是这两处断言写死了当时的 Bug 条数，而库在我开工前刚变过（`data/` 目录 16:22 有改动）。
已按项目既有风格改成从库里算。
